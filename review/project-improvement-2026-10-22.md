## 核心判断与品味评分

**值得改进，优先解决数据正确性、文件边界和任务生命周期。品味评分：还行，但需要收紧状态和标识的设计。**

`Segment(start, end, text, spk, conf)` 用秒统一时间，CLI/Web 共用转写管线，AI 失败与转写成果分离，这些基础是对的。当前最严重的问题出现在边界：句子结束后切点状态未清空、完整文件名被误当成扩展名、片内说话人编号被当成全片身份、后台线程与数据库任务状态没有统一的所有者。

本轮没有认定 P0 问题。下面的 P1 表示可造成错误结果、文件覆盖、服务失去响应或越过实际使用边界，应优先处理；P2 表示工程与维护改进。“已复现”均注明具体输入或隔离方式，不代表已测出真实课堂数据中的发生率。

## R1：文件访问边界由服务端确定

位置：[静态文件路由](/E:/classroom-asr-ascii/asr/web/__init__.py:215)、[读取 LLM 设置](/E:/classroom-asr-ascii/asr/web/__init__.py:742)、[保存 LLM 设置](/E:/classroom-asr-ascii/asr/web/__init__.py:755)。

静态路由仅执行 `STATIC_DIR / path`，随后检查文件是否存在，没有确认规范化后的路径仍在静态目录内。子代理把静态目录和一个无敏感内容的 canary 文件置于独立临时目录，用 TestClient 验证目录外 canary 可被返回，HTTP 200。未读取真实用户文件。

设置接口允许客户端传入 `config` 路径。保存时只要求目标是已有文件，并不要求它是应用配置；对合成的普通 `.txt` 文件保存 LLM 设置，会返回 200 并在其中追加配置节。设置读取接口还会返回完整 `api_key`。默认本机运行已有文件范围缺口；README 支持的 `--host 0.0.0.0` 局域网运行方式会扩大可访问者范围。这里不假设公网部署。

最小改进：静态文件采用框架的受限静态目录服务，或在路径规范化后检查所属目录；Web 配置文件由服务端启动参数固定，客户端只提交配置值。局域网模式增加最低必要的访问控制，读取设置时返回密钥是否存在及脱敏值，保存时区分保留、替换与清空。CLI 的显式本地配置路径能力可以继续保留。

兼容风险：自动化客户端如果正在通过 HTTP 传任意配置路径，需要迁移到服务端登记的配置标识；页面默认配置流程可保持一致。

## R2：句子提交后清空全部切点状态

位置：[强标点分支](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:664)、[软切段执行](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:693)、[无效段删除](/E:/classroom-asr-ascii/asr/postprocess.py:156)。

前一句包含逗号并以句号结束时，强标点分支清空 `buf` 和 `t0`，没有清空 `cut/cut_end_t/next_t0`。下一句超过 8 秒且没有先遇到新切点时，会使用上一句的时间和缓冲位置。

轻量复现输入：

```python
text = "甲，乙。" + "一二三四五六七八九十" * 2 + "。"
ts = [[i * 500, i * 500 + 400] for i in range(22)]
segs = _split_by_char_ts(text, ts, duration_s=15)
clean = validate_timestamps(segs, duration_s=15)
```

实测切段结果包含 `[1.0, 0.4, "一二"]`，下一段起点还回退到 `0.5` 秒。后处理删除反向时间段后，“一二”永久丢失；文字守恒检查为 `False`。

最小改进：把“提交当前段”和“重置当前段状态”放在同一处，清空所有属于该段的切点。回归用例必须跨过“含软标点的短句 → 强标点 → 超长下一句”，同时断言文本守恒、每段 `start <= end` 和无意外时间回退。

这不是模型识别质量问题，是确定性的代码错误。只修改该状态转换，保持秒制 `Segment` 和产物结构不变。

## R3：文件名是标识，不应再次剥扩展名

位置：[pipeline 构造 base](/E:/classroom-asr-ascii/asr/pipeline.py:235)、[多格式输出](/E:/classroom-asr-ascii/asr/srt.py:224)、[替换日志](/E:/classroom-asr-ascii/asr/pipeline.py:256)、[保留 WAV](/E:/classroom-asr-ascii/asr/pipeline.py:263)、[临时目录清理](/E:/classroom-asr-ascii/asr/pipeline.py:269)。

pipeline 已经剥掉媒体扩展名，writer 再调用 `with_suffix()`，把输入名字中的 `.1`、`.2` 当成后缀替换。向同一目录依次写入两个不同内容的识别结果，实际得到：

```text
base=lesson.1 -> lesson.json
base=lesson.2 -> lesson.json
目录只剩 lesson.json；第一次返回的路径读到 second。
```

其余输出格式和 `replace.log` 使用相同命名方式。CLI 批量处理最容易遇到；Web 每任务目录隔离能避免不同任务互相覆盖，但文件名仍会被截断。

`keep_wav` 还有同类问题：不同输入都保存为 `_wav/audio.wav` 或 `_wav/audio_denoised.wav`，子代理用两份不同的临时 WAV 验证第一份被覆盖。保留文件已经复制到输出目录后，`finally` 仍跳过整个临时目录的清理。

最小改进：在完整 `base.name` 后追加产物扩展名，批量任务执行前检查最终路径冲突；保留 WAV 使用输入唯一名称，复制完成后清理工作目录。对不同目录下完全同名的输入，也应明确拒绝冲突或分配子目录。

兼容风险：带点文件名的新产物名称会改变，应通过任务元数据登记实际文件名，保留旧任务下载查找能力。

## R4：不支持的数字应保持原文

位置：[百分数匹配范围](/E:/classroom-asr-ascii/asr/postprocess.py:28)、[中文数字解析](/E:/classroom-asr-ascii/asr/postprocess.py:31)、[ITN 调用](/E:/classroom-asr-ascii/asr/postprocess.py:61)。

直接调用 `apply_itn()` 的实测结果：

| 输入 | 当前输出 |
|---|---|
| 百分之一百二十 | `10%` |
| 百分之三点五 | `3%点五` |
| 百分之九十九 | `99%` |
| 二〇二三年 | `2023年`，该历史问题已修复 |

数字解析先处理“十”，遇到“一百二十”时把不认识的“一百”默认为 1；正则不支持小数，却会先转换小数前面的整数部分。默认开启的后处理会把模型原本正确的文字数值改错。

最小改进：只转换完整且确定支持的数词。不能解析完整数值就保留原文，补上百位、小数、负数等边界测试后再扩展支持范围。不要通过继续增加宽泛正则去猜数值。

## R5：Markdown 解析器必须保证每轮前进

位置：[块起点判断](/E:/classroom-asr-ascii/asr/mdrender.py:45)、[主循环](/E:/classroom-asr-ascii/asr/mdrender.py:49)、[段落循环](/E:/classroom-asr-ascii/asr/mdrender.py:97)、[AI 阅读接口](/E:/classroom-asr-ascii/asr/web/__init__.py:356)。

`render_markdown("| orphan")` 会被判断为块起点，却不满足表格条件，也不满足标题和列表分支；段落循环拒绝消费这一行，外层循环仍保持 `i=0`，反复追加空段落。

本轮用 `sys.settrace` 在外层循环重复 100 次后主动中断，实际状态为 `i=0, n=1, iterations=101`。没有让循环无限运行。它会使对应阅读请求不返回，并持续占用线程和内存。

现有 [test_lone_pipe_line_not_table](/E:/classroom-asr-ascii/tests/test_mdrender.py:99) 使用的是“他说：| 分隔符”，竖线并不在行首，因此没有覆盖测试注释描述的场景。

最小改进：块起点判断与实际可解析块保持一致；无法识别的行作为普通文本消费，确保所有分支都推进游标。补行首孤立竖线、不完整表格和表格附近普通文本的案例。现有先转义 HTML 的做法应保留。

## R6：启动器不能强杀端口上的任意进程

位置：[run_web.bat:8](/E:/classroom-asr-ascii/run_web.bat:8)。

脚本从 `netstat` 中找包含 `:8765` 的监听行，直接执行 `taskkill /f`，未检查进程归属。只要其他服务占据该端口，双击启动器就会强制终止它。用户传入其他 `--port` 时，这段清理仍针对固定 8765。该结论来自脚本原文，本轮没有实际运行杀进程命令。

最小改进：移除无条件强杀，端口被占用时报告错误并允许更换端口。如果需要“重启本项目”，只管理本启动器登记且验证过的实例。

这是优先级很高、改动很小的兼容性修复：应用启动不应破坏同机其他程序。

## R7：让任务状态和执行者拥有同一套生命周期

位置：[启动与关闭](/E:/classroom-asr-ascii/asr/web/__init__.py:174)、[删除任务](/E:/classroom-asr-ascii/asr/web/__init__.py:595)、[AI 准入](/E:/classroom-asr-ascii/asr/web/__init__.py:798)、[看门狗](/E:/classroom-asr-ascii/asr/web/__init__.py:1004)、[任务收尾](/E:/classroom-asr-ascii/asr/web/__init__.py:1192)。

目前用 SQLite 持久化状态、用 daemon 线程执行工作，缺少统一的执行者登记和状态协调，产生四个相关缺口：

1. **重启遗留任务**：启动只建表和建目录，没有把上次进程留下的 `pending/running` 恢复、标记中断或重新排队。记录留在“处理中”，实际执行线程已经消失。
2. **并发准入**：AI 重跑先 `SELECT status`，随后才 `UPDATE running`。子代理让两个调用在配置加载处通过 Barrier 同步，二者都先看到 `done`，最终均返回 202，并登记两个 worker。没有启动真实 AI。并发运行可能重复调用 LLM，元数据的读改写也可能互相覆盖。
3. **运行中删除**：删除接口无运行状态检查，直接删除数据库行和磁盘目录；后台任务没有取消标志。之后仍可能写出孤儿文件，收尾查询已删除记录时也缺少判空。这是源码可见的竞态路径，本轮未对真实任务执行删除。
4. **超时与资源释放不等价**：看门狗标记失败并设置异常标志，主线程在 `pipeline_run()` 返回后才读取该标志。若底层推理真正卡死，线程和模型资源不会因为界面已显示失败而被终止。

最小改进：保留 SQLite 和单体部署，增加一个任务执行管理器。先用数据库条件更新 `UPDATE ... WHERE status='done'` 抢占任务，再检查受影响行数；在启动时把遗留任务标记为中断，并区分“转写中断”和“仅 AI 中断”，保住已完成转写。运行中的任务先取消并等待结束再清理，或明确拒绝直接删除。

执行资源应有容量上限，关闭时先停止接收任务、处理在途任务，再释放引擎。硬性终止卡死推理若确实是刚需，才考虑工作进程隔离；普通 Python 线程没有可靠的强制终止机制。此处不需要引入 Redis、Celery 或独立调度服务。

## R8：缓存身份必须覆盖实际模型与推理配置

位置：[缓存键](/E:/classroom-asr-ascii/asr/pipeline.py:61)、[引擎保存配置](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:36)、[推理参数](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:424)。

缓存键包含 ASR 模型、设备、质量等，但缺少 `language` 和 VAD/PUNC/SPK 模型路径。引擎保留第一次创建时的整个可变 `cfg`。子代理构造两份配置，只修改语言和 VAD 路径，实测 `build_engine()` 返回同一实例，第二次仍持有第一份的语言和 VAD 路径。

因此连续任务或长驻进程更改配置后，实际执行不一定采用新配置。batch 的每任务深拷贝解决了直接共享 `cfg` 的历史问题，却没有消除缓存实例继续持有旧配置的问题。

当前源码也没有模型加载或推理锁。缓存插入、惰性加载、生成与关闭之间的并发没有统一保护；这属于资源可靠性风险，本轮没有用真实模型压测，不能声称已经测得重复模型占用或真实推理串结果。

最小改进：把不可变的模型加载配置和每任务参数分开；模型缓存键覆盖所有加载依赖，语言等推理参数显式随任务传入。加载与释放由管理器统一协调，在证明模型可并发前按实例串行调度。不要只继续给一个保留整个 `cfg` 的缓存键零散补字段。

## R9：AI 成功必须意味着完整结果已可靠发布

位置：[LLM 响应解析](/E:/classroom-asr-ascii/asr/llm.py:57)、[AI 文件写入](/E:/classroom-asr-ascii/asr/web/__init__.py:1153)、[旧文件回退](/E:/classroom-asr-ascii/asr/web/__init__.py:294)。

第一，客户端只读取 `message.content`，没有检查 `finish_reason`。本轮 mock 返回非空正文与 `finish_reason="length"`，`chat()` 直接返回不完整正文，后续会按成功产物保存。该结束原因表示输出达到请求的 token 上限，可参照 [OpenAI Chat API 官方说明](https://developers.openai.com/api/reference/resources/chat)。课堂长稿更需要暴露这种不完整状态。

第二，重新生成直接 `write_text()` 覆盖最终文件。本轮在临时目录准备“上次完整版本”，模拟写入部分字节后出现 `OSError`。最终结果是：该件有错误、成功登记已清空，但旧完整内容已经丢失；下载回退仍能找到文件，返回的却是 `PARTIAL`。

最小改进：检查返回结构、正文类型和结束原因，将截断标为不完整，不能当完整成稿发布。先写同目录临时文件，完整校验成功后原子替换最终文件，再更新登记；失败保留上一版，并明确区分历史版本和本次结果。

全文一次发送的设计还需要增加模型上下文预算和明确的超长提示。先记录长度及结束原因，再根据真实长课样本决定是否按教学结构分块；不要只加大 `max_tokens` 或在 prompt 中要求“不要遗漏”。分块并合并能否保住知识点，需要另外验收。

## R10：测试应证明关键行为，且能脱离个人环境运行

位置：[依赖个人配置的夹具](/E:/classroom-asr-ascii/tests/test_funasr_engine.py:11)、[依赖本地模型的单测](/E:/classroom-asr-ascii/tests/test_config.py:44)、[现有 AI E2E 方案](/E:/classroom-asr-ascii/docs/superpowers/plans/2026-10-21-ai-feedback.md:1578)。

现有测试覆盖面不算少，也有不少历史问题的回归用例。但部分测试仍加载不进仓库的 `config.yaml`，一个普通配置测试要求模型已下载；AI E2E 脚本按历史计划放在 TEMP 且不入库，仓库跟踪文件中未发现持续集成配置。历史“E2E 24/24”不能当作本轮已重跑结果。

建议建立三层验证：

1. 默认单测只使用模板、最小临时配置与目录夹具，不依赖个人密钥和模型下载。
2. 轻量集成检查使用临时 SQLite、真实文件写入、fake 引擎和 fake LLM，覆盖时间戳文字守恒、带点文件名、并发准入、重启、失败写入和读取降级。
3. 显式启用的真实模型验收保留少量有代表性的录音：长静音、数字与术语、多人轮换、重叠语音。记录环境、模型版本和人工标注依据。

将可复现脚本和测试入口入库，先把默认单测接入轻量 CI。优先补本轮暴露的跨步骤案例，不把测试数量增加当成质量提升。

## R11：安装与运行应使用同一份版本契约

位置：[Python 元数据](/E:/classroom-asr-ascii/pyproject.toml:9)、[README 安装说明](/E:/classroom-asr-ascii/README.md:15)、[setup 解释器选择](/E:/classroom-asr-ascii/setup.bat:11)、[启动解释器](/E:/classroom-asr-ascii/run_web.bat:20)、[依赖下界](/E:/classroom-asr-ascii/requirements.txt:1)、[模型下载](/E:/classroom-asr-ascii/scripts/download_models.py:45)。

`pyproject.toml` 声明 `>=3.10,<3.12`，README 却说明 3.12 可跑，本轮测试也确实运行在 3.12.10。用 `packaging.SpecifierSet` 检查当前版本，结果为 `False`。`requires-python` 会影响包的安装兼容判断，见 [PyPA 官方说明](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/#requires-python)。

`setup.bat` 可以回退到 PATH 上的 `python`，`run_web.bat` 却固定使用 `py -3`；多解释器机器可能安装和运行使用不同环境。项目元数据也未声明运行依赖，依赖只列在 `requirements.txt`；目前主要通过源码运行，尚未把包安装当本轮验收入口。

依赖几乎只有 `>=` 下界，模型下载未固定 revision。同一提交不同时间安装，识别栈和模型内容可能变化。需要建立经过验证的 CPU 环境约束和模型 revision 清单，再把 GPU 作为独立验收环境；保留合理的依赖范围，不要求把所有用户永久锁在某一版本。

最小改进：安装器创建项目虚拟环境，启动器复用同一个解释器；根据真实验证结果统一 Python 支持范围、项目依赖与文档。README 双击启动地址写的是 8000，而脚本实际使用 8765；模块直接启动默认 8000 是另一条正确说明，不能全局替换。

## R12：在修清状态之后按职责拆分

当前 [Web 模块](/E:/classroom-asr-ascii/asr/web/__init__.py:1) 约 1235 行，同时负责数据库、路由、上传、导出、任务调度、AI 编排和配置保存；[FunASR 引擎](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:1) 约 721 行。行数本身不构成缺陷，但多个生命周期和路径规则聚集在这里，已经增加修改时遗漏交互的风险。

建议在保持现有 HTTP 路径、数据库字段和产物格式的前提下，提取四个明确职责：任务仓库、任务执行管理器、产物定位与发布、HTTP 路由。AI 生成复用产物发布与任务状态能力，不再各自做状态读改写。不要为每个小函数增加一层服务对象。

[抽象引擎接口](/E:/classroom-asr-ascii/asr/engines/base.py:39) 未声明 pipeline 实际传入的 `on_progress/on_segments`，`_quality_override` 也依赖隐式私有属性。将任务选项和回调契约显式化，可减少多处同步修改与类型检查盲点。只支持一个引擎的现状下，保留必要接口即可，不需要建设插件平台。

## V1：说话人身份需要跨组验收

位置：[逐组识别](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:333)、[原样保留组内 spk](/E:/classroom-asr-ascii/asr/engines/funasr_engine.py:347)、[全片时长聚合](/E:/classroom-asr-ascii/asr/diarize.py:27)。

每个 VAD 组独立调用识别，只偏移时间、原样保留 `spk0/spk1`，随后按字符串在整片聚合。子代理检查本机安装的 FunASR 1.4.16 源码，确认每次结果独立聚类并从 0 开始编号。两个组各自只有一个说话人时，局部 `spk0` 不代表同一个真实人。

mock 两组分别包含教师、学生，且两组局部 ID 都是 0，当前流程会将二者都标为“教师”。这证明当前数据标识缺少作用域；没有真实多人录音验收，因此不声称所有真实录音都会串人。

最小方向：明确说话人 ID 的作用域，增加跨组声纹匹配或独立全片聚类；仅给 ID 加组前缀也不能解决同一人跨组的归并。完成前，把角色和互动统计定位为启发式结果，在有人工标注的小样本上验收，再判断是否需要更复杂模型。

## 数据流、性能与兼容性上的关键结论

- 数据流是“配置＋媒体 → 秒制 Segment → 后处理 → 产物”，Web 还要维护“数据库记录 ↔ 工作线程 ↔ 文件”。最值得简化的是后一个三方所有权关系。
- 应保护三个事实：文字不因时间戳修复而丢失、产物名称不会把不同输入合并、任务终态对应真实执行状态。围绕这三点增加验证，比扩大抽象层更直接。
- 当前逐组转写使用 WAV 定位读写，不能简单声称项目把整堂课一次全部读进 Python 内存。本轮没有测得内存峰值，长音频内存问题保留为待测。
- 增量 transcript 仍每组序列化并写回全部累计内容；[前端](/E:/classroom-asr-ascii/asr/web/static/task.js:104) 每秒轮询完整状态。规模增长后可能产生累计写入和传输成本，但没有本轮性能数据，不把它定为已测出的主要瓶颈。先记录时延、数据库写入量和请求体积，再决定是否引入游标增量接口。
- 前端已有约 80 段 DOM 上限，Markdown 已先转义 HTML，AI 单件失败已做隔离。这些有效的约束应保留。
- 修复时保持现有 CLI 参数、HTTP 路径、SQLite 旧任务、输出结构和本地离线工作流；确实需要改变文件名时，使用显式登记和旧任务兼容读取。

## 建议实施顺序

1. 先处理 R1、R6：收紧文件边界，移除启动器无条件强杀。它们关系到用户文件和同机其他程序。
